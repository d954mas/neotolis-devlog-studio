# Long-form devlog playbook

Практический стандарт для горизонтального девлога длиной 6–12 минут.
Основан на разборе всех длинных видео Zerah Games и двух наших
`Not a Trolley Problem` devlogs. Подробные доказательства:
`docs/ZERAH_DEVLOG_BENCHMARK.md`.

## North star

Не «рассказать, что было сделано», а провести зрителя через одну
трансформацию, разбитую на законченные микроистории с видимым
доказательством.

Зритель должен уметь ответить:

1. Что было сломано, сложно или странно?
2. Почему первая версия не сработала?
3. Какое решение принял автор?
4. Где видно, что теперь работает?
5. Что автор об этом думает или чувствует?

## До сценария: evidence-first

1. Скопировать
   `tools/devlog_reference_lab/templates/story_map.example.json` в
   `<production>/data/plan/story_map.json`.
2. Сформулировать один `macro_question`, на который ответит финал.
3. Запланировать минимум `max(4, ceil(duration / 90s))` микроарок.
   Для 8–12 минут рабочая цель — 6–10.
4. Для каждой арки назначить реальные sources:
   `before`, `failure` или `process`, `payoff`.
5. Снять missing evidence до финального текста. Если failure/payoff не
   существует, материал пока не является полноценной аркой.
6. Выполнить раннюю проверку:

```powershell
dl2 longform-check <product:production>
```

`needs_capture` на этом этапе — предупреждение. Перед записью финального
VO выполнить тот же вызов с `--strict`: unresolved sources блокируют
производство.

## Структура 8–12 минут

Это диапазоны, а не монтаж по секундомеру:

| Время | Функция |
|---|---|
| 0:00–0:08 | реальная аномалия/сбой + glimpse результата |
| 0:08–0:15 | продукт и конкретное обещание эпизода |
| 0:15–0:35 | краткий контекст и ставка; без полной предыстории |
| 0:35–8:30+ | 6–10 микроарок, сгруппированных в 2–4 главы |
| последние 30–60 с | ответ на macro question, честный статус, одна следующая петля |

Одна арка:

> цель → плохая версия → причина → решение → proof → реакция

Не каждую арку нужно проговаривать одинаково. Но `before` и `payoff`
должны быть видимы, а failure/process — доказаны кадром, а не только
утверждением VO.

## Правила сценария

- Одна фраза выполняет одну функцию: вопрос, причина, решение, proof или
  реакция.
- Убирать служебную хронологию «потом я сделал…» там, где её можно
  заменить причинностью «это сломало X, поэтому я попробовал Y».
- Русский VO: целиться в 150–165 wpm. Оставлять паузы на визуальный proof,
  шутку и смену главы.
- Одна человеческая реакция каждые 45–75 секунд: цена решения, сомнение,
  ошибка, неожиданность, мнение, самоирония.
- Одна макропетля плюс 3–5 микропетель. Каждую обещанную петлю либо
  закрыть, либо честно переопределить в финале.
- Не объяснять код, если зрителю достаточно увидеть проблему, принцип
  решения и изменение поведения игры.

## Capture plan

Материал снимается по роли, а не «всё подряд»:

| Роль | Что снять |
|---|---|
| before | нормальное состояние до изменения |
| failure | конкретный баг, плохая версия или ограничение |
| process | один понятный эксперимент, debug view, Blender/Unity/code |
| payoff | чистое действие, где результат считывается без VO |
| reaction | лицо/голос/короткая авторская оценка, если уместно |

Для каждого gameplay capture сохраняются build/state identity, native
geometry, capture method и 5-секундные handles по правилам
`$devlog-record-media`. Frame-stepped DevAPI — только debug/presentation
proof, не обычный gameplay.

## Монтажная грамматика

- Смысловое изменение кадра каждые 3–6 секунд.
- Один master shot — максимум около 8 секунд без нового действия,
  ракурса или callout.
- Before/after показывать в одной визуальной системе, чтобы разница
  читалась мгновенно.
- Крупный gameplay proof важнее декоративной инфографики.
- Текст — 5–7 слов на экран; диаграмма только когда она объясняет реальную
  причинность.
- Не превращать scene-event count в KPI: contact sheet и просмотр exact
  MP4 обязательны.
- Новые motion/infographic assets делать только через HyperFrames и
  возвращать в обычный Beat/Chunk pipeline.

## Звук

- Delivery остаётся на проектном стандарте −14 LUFS; повышение громкости
  не решает проблему удержания.
- Для 8–12 минут планировать 2–3 музыкальные фазы, соответствующие главам.
- 8–15 тихих stingers/SFX на переходы, failures и payoffs — ориентир, не
  квота.
- Музыка отступает перед ключевой причиной, шуткой и первым чистым
  показом результата.
- Лицензирование — по AGENTS.md: CC0/public domain/purchased
  no-attribution в приоритете.

## Thumbnail и title

- Один реальный proof-кадр из ролика или ясный before/after.
- Один главный объект; 0–3 слова.
- Номер devlog — вторичный, не основное обещание.
- Title называет проблему, риск или трансформацию.
- Thumbnail и первые 15 секунд должны обещать один и тот же ролик.
- Для long-form подготовить три разные пары title/thumbnail: curiosity,
  number, outcome. Это три гипотезы обещания, а не одна обложка в трёх цветах.
  После публикации использовать native YouTube A/B test и оценивать победителя
  по watch time, не по CTR в отрыве от удержания.

Формулы title:

- «Я переделал X, потому что Y всё ломал»
- «Почему простая X стала худшей проблемой игры»
- «N дней, чтобы превратить X в Y»
- «Я добавил X — и сломал Y»

## Production loop

1. Story map и ранний validator.
2. Бounded source capture; missing material временно закрывается
   placeholders только для scratch draft.
3. Scratch VO и первый `dl2 preview`.
4. Слепой `video-reviewer`: сначала review pack, затем exact frames только
   по конкретным аномалиям.
5. До трёх improve-итераций; пять — hard cap.
6. Перед final VO — `dl2 longform-check <product:production> --strict`.
7. Перед `dl2 final` — `docs/CHECKLIST_LONG_DEVLOG.md`.
8. Exact final review, три A/B package hypotheses, package и delivery.
9. SHA-verified archive полного publish-пакета через
   `tools/publish_archive.py`, затем один `devlog-reflector`.

## Следующий ролик: рекомендуемый MVP

Не начинать с 12 минут. Следующий выпуск:

- 7–9 минут;
- одна трансформация;
- 5–6 доказанных микроарок;
- cold open из реального failure/payoff;
- 2 музыкальные фазы;
- один thumbnail proof без `DEVLOG 2` как главного текста.

Критерий успеха первой итерации — не просмотры, а то, что слепой reviewer
может назвать все арки, их failures и payoffs без чтения production notes.
